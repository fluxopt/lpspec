# Review: `lpspec.strategy` and `solve_over`

> **Prompt:** Review the strategy module and the solve_over api. What can be improved? What common problems will users face when using it? How can we help them? Can the module be simpler? What else could be added?

> [!NOTE]
> The following content was generated by AI. Checked against `main` at lpspec `98b0671` and math-spec `ae6ba35` (2026-09-08). Every problem in the table below was reproduced by running, not only by reading; the script and its output are at the end.

## Verdict

The design is right: one fold, two axes, a hand-built list as the escape hatch, and every rule checked before data is read. The problems are at the edges of that design, and four of them are real bugs a user hits on their first non-toy sweep. The module can lose one concept and one false claim, and the most valuable addition is a way to reproduce a single slice.

## Problems users will hit

In the order a user meets them:

| # | What happens | Where |
|---|---|---|
| 1 | The `sources` dict that works with `solve` fails in `solve_over`. A scalar (`soc_initial: 0.0`), a bare `range` index, or a `{label: value}` map raises `cannot slice a source of type float`, even when that source does not carry the axis. Every test fixture and both examples wrap scalars in a `pl.DataFrame`, which is the workaround made habit. | `strategy.py:1092`, `:1069`, `:1048` |
| 2 | A source that lacks one coordinate of the axis is silently built empty for that slice. With `cost` missing period 3, period 3 solved to objective `0.0` with no warning. | `strategy.py:1098` |
| 3 | A carried sweep where one slice is infeasible dies with a raw `KeyError: 'soc'`. The docstring promise that a failed slice does not fail the sweep is broken exactly where it matters. | `strategy.py:849` |
| 4 | A carry index in the lookahead is accepted silently. `EachWindow(6, 3)` with `carry=('soc', 5)` runs and hands forward a level the next window recomputes. `sweeps.md` calls this the trap, and the code does not catch it. | `strategy.py:95` |
| 5 | No seed for the carried parameter gives the generic `no data provided for parameter 'soc_initial'`, with no hint that the carry supplies it from slice two on. | `strategy.py:95` |
| 6 | A slice that fails after others solved loses everything, and the error does not name the slice. On a 50-window sweep that is the whole afternoon. | `strategy.py:837`, `:886` |
| 7 | `ordered=True` on string coordinates sorts `p1, p10, p2`, so the carry chain runs in the wrong order silently. | `strategy.py:1098` |
| 8 | `key_name='value'` raises a polars `DuplicateError`; `key_name='status'` silently drops the key column from `objective`. The collision check only covers dimensions. | `strategy.py:983` |
| 9 | The pooled branch re-reads and re-lowers the YAML once per slice. The `solve_over` docstring and `sweeps.md` both claim no worker reads it again. A `Spec` pickles in about a kilobyte, so handing workers `to_spec(spec)` makes the claim true. | `strategy.py:945`, `:726`, `docs/reference/sweeps.md:170` |

### How to help

- **1 and 2 share a fix.** In `_coordinates`, only table-shaped sources are asked for a schema; everything else passes through untouched, and `_encode` pickles a scalar as itself. Then, per carrying source, check that it covers every coordinate the union found and refuse with the source and the missing coordinate named. That check is one `group_by` and turns a silent zero into a load-time error, which is the project's whole promise.
- **3, 4 and 5 are three sentences in `_CarryRule`.** The parameter must be in the sources, said as "the first slice needs a seed". An `EachWindow` carry with `index >= step` is refused, naming `step - 1`. A slice with no primal under a carry raises a `LpspecError` that names the slice, its termination condition, and that the next slice had nothing to start from.
- **6 is a wrap.** Re-raise a slice's exception with its key and position prefixed. Partial results belong to the spill decision in [#610](https://github.com/fluxopt/lpspec/issues/610), and should not be solved here.
- **7 is a sentence in the docs**, unless `ordered` is dropped as below.
- **8 extends the existing check** to the four fixed column names: `value`, `status`, `termination_condition`, `objective`.
- **9 is a one-line change** in `_pooled`: hand the worker `to_spec(spec)` rather than the raw path, and the docstring claim becomes true.

## Can the module be simpler

Yes, in two places.

- **Drop `ordered`.** It changes no behaviour; it only gates `carry`. The order is sorted coordinate order either way, which is what `runs.keys` shows, and problem 7 shows the flag does not make the sequence right. A carry on `EachCoordinate` is the caller saying the coordinates are a sequence. One field, one check and one error message go away (`strategy.py:261`, `:787`).
- **Cut the `solve_over` docstring to the caller's terms.** Half of it narrates internals, which the project's own docstring rule sends to the code, and one paragraph is false (problem 9). The rules already live in `sweeps.md`, which it links.

Keep the executor path and its wire, tri-state `workers_share_fs` included. It is the one extension point, and the tests hold it to the serial branch's answers.

## What to add

One thing first: **make the cuts public.** `EachWindow.cuts(sources)` and `EachCoordinate.cuts(sources)`, returning the `(key, sources)` list the hand-built axis already accepts. It answers the question every user with an infeasible window 37 asks:

```python
cuts = lps.EachWindow('snapshot', 48, 24, into='t').cuts(sources)
lps.build('spec.yaml', cuts[37][1]).write('w37.lp')
```

It also composes, so scenario × window is a nested comprehension over two `cuts` calls rather than a third class, and it costs a rename of a private method.

Second: **a time column in `runs.objective`.** Build and solve seconds per slice, which `Model.diagnostics` already measures. Nothing today says which slice was slow.

Not worth adding: a progress callback, a per-slice reader, an aggregate objective. The first is a seam nothing needs yet; the docs argue against the other two well.

## Suggested order of work

Each is one PR, tests first as strict `xfail`, stacked:

1. `fix(strategy): a sweep takes every source shape solve takes, and refuses a source that misses a coordinate of the axis` (problems 1, 2)
2. `fix(strategy): a carry names its seed, refuses an index in the lookahead, and says which slice left nothing to carry` (problems 3, 4, 5)
3. `fix(strategy): a failing slice is named, and a key that collides with a fixed column is refused` (problems 6, 8)
4. `fix(strategy): a pooled sweep parses the model once` (problem 9)
5. `refactor(strategy): a carry needs no ordered flag` and the docstring cut
6. `feat(strategy): an axis hands out its cuts, so one slice can be built alone`
